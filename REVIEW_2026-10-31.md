# Redpen Voice: bug hunt and quality review, 2026-10-31

Branch: `claude/redpen-voice-quality-review-0w7qha`, starting from `main` at `214c216`.

I read every source file: all of `Sources/RedpenVoice`, `Sources/VoiceCore`, `Sources/redpen-voice-test`, `Tests`,
`Package.swift`, `build.sh`, `release.sh` and the entitlements. Line numbers below are for `main` at `214c216`, the
code as it was before this branch, unless a line says "branch".

**Read this first: what was and wasn't verified.** This review ran in a Linux container with no Mac, Xcode,
microphone or display. So:

- The new tests and the VoiceCore files they cover were compiled and run on Linux with Swift 6.1.2 (25 XCTest
  cases, 0 failures, including the 5 existing `MediaPauseTests`).
- **The app target (`RedpenVoice`) was not compiled.** It needs AppKit, AVFoundation, WhisperKit and the macOS 26
  SDK. Every fix in it is small and was written carefully, but it has not been built. Before merging, run
  `swift build -c release --product RedpenVoice`, `swift test` and `swift run -c release redpen-voice-test` on a Mac.
- Nothing was run against real hardware. "Confirmed" below means I traced the failure through the code, or
  reproduced it with a standalone program where the code allows that. It does not mean I saw it on a Mac.
  "Unconfirmed" means it depends on macOS behaviour I couldn't check here.

The worst items I found:

1. One stuck speech-engine job could leave Voice unable to start any new dictation until you quit it, and the quit
   itself could hang.
2. One missing or mistyped key in `config.json` reset every setting, and the next change in Settings wrote the
   defaults over the file.
3. After the mic failed to start or went away (Bluetooth dropping, an interface unplugged), every later press
   recorded silence until a relaunch.

All three are fixed on the branch.

## Bugs, most serious first

### 1. A stuck Whisper or Fast ending makes Voice deaf until you quit it, and the quit can hang. **Fixed** (`b9e7e32`)

- **Where:** `main.swift:1575` (`raw = try await s.finish()`, with no time limit), `main.swift:537-540` (`canBegin`
  requires `writing == 0`), `Transcriber.swift:780-811` (the Whisper ending has no deadline) and `:751-754`
  (Parakeet has none either). Compare with the Mac engine, which has a 10-second limit at `:815-828`, and Instant,
  which has its own deadline at `:762`. `main.swift:649-659` asks to quit later and waits for that same `end()`.
- **What goes wrong:** `end()` adds the dictation to `writing` and only removes it once `finish()` returns. While
  `writing > 0`, `TalkKeyState` swallows every talk-key press. If WhisperKit or the Neural Engine never answers,
  the bar stays on "Writing", no press ever starts a dictation, and Quit while talking (`terminateLater`) waits
  forever. That blocks logout and shutdown too.
- **How to make it happen:** Make a Whisper job hang (the code already retries "ANE op async execution failed",
  so the Neural Engine does misbehave), for example under heavy Neural Engine load from another app. Then try to
  dictate again. *Unconfirmed* whether WhisperKit can hang outright rather than throw. The lock-out that follows
  is confirmed in the code.
- **Fix:** `Deadline.run` (VoiceCore) runs the ending against a time limit of 30 s plus 0.5 s per second
  recorded. On timeout it cancels the session, logs it, and the bar says writing was stopped. The next press then
  works. A Whisper job that hung for good would still hold Whisper's one-job queue, so later Whisper endings would
  time out too, but the app tells you and stays usable. A follow-up could reload WhisperKit after a timeout, the
  way `replaceStuckLive()` does for Instant.

### 2. One missing or mistyped key in `config.json` resets every setting, and the next change overwrites the file. **Fixed** (`b09f0dd`)

- **Where:** `Config.swift:5` (synthesized `Codable`) and `:84-92` (`load()` returns `Config()` on any decode
  error). The overwrite happens at `SettingsWindow.swift:10` (`didSet { config.save() }`), in `setMode`
  (`main.swift:1786-1789`) and in `FirstRunModel.update`.
- **What goes wrong:** Swift's synthesized decoder ignores default values, so every non-optional key (`mode`,
  `engine`, `sounds`, `inputDevice`, `showLevel`, and others) must be present with the right type. If one isn't,
  the whole file fails to decode. Voice then runs with the defaults: the Mac engine, Fn or right Option as the
  talk key, `firstRunDone = false` (so the first-run window comes back), and the default mic. The next toggle in
  the menu or Settings saves those defaults over the user's file.
- **How to make it happen:** Delete the `"sounds"` line from `config.json`, or write `"typingWPM": "60"`, then
  relaunch. I reproduced the decode failure with a standalone copy of the struct: `keyNotFound(... "sounds" ...)`.
  The README says the file "can be read and edited by hand", so hand edits are expected.
- **Fix:** `Config` moves to VoiceCore so it can be tested. Its decoder now reads each key on its own and uses
  the default for any key that is missing or has the wrong type. A file that isn't JSON at all is moved to
  `config.damaged-<time>.json` before the defaults are used, so what the user typed is never overwritten. A
  `typealias` in the app keeps the name `Config` unambiguous next to the speech frameworks.

### 3. After the mic fails to start or goes away, every press records silence until a relaunch. **Fixed** (`f8fb4d8`)

- **Where:** `Recorder.swift:69-100` (`start()` calls `stopEngine()` first, then can throw at `:76`, `:78`, `:79`
  or `:92`), `:136-140` (`stopEngine()` kept `inputName`), `main.swift:850` (a press opens the mic only
  `if recorder.inputName.isEmpty`). Nothing watched for the capture device disconnecting.
- **What goes wrong:** If a restart fails (Settings mic change, the default input moving, the device busy or
  gone), the old capture is already stopped but `inputName` still names it. `begin()` therefore never retries, and
  the HUD then says "No sound from <old mic>" or "Didn't catch that" on every press. If a USB interface is
  unplugged, or a Bluetooth headset drops while it's the chosen mic (not "Same as the Mac"), the capture session
  delivers nothing and nothing notices: `remicIfDefaultMoved` is skipped when a specific mic is chosen
  (`main.swift:728`).
- **How to make it happen:** In Settings pick AirPods as the microphone, then put the AirPods in their case and
  press the talk key. Or pick a USB interface and unplug it.
- **Fix:** `stopEngine()` clears the mic's name and id. The recorder now watches
  `AVCaptureDevice.wasDisconnectedNotification` and `AVCaptureSession.runtimeErrorNotification`; on either it
  stops capture, and the app opens a mic again a second later (or at the next press if a dictation is running).
  If the chosen mic is missing, `start()` already falls back to the default input.

### 4. A Bluetooth headset drops to call-quality audio for as long as Voice runs. **Not fixed.** Likely

- **Where:** `Recorder.swift:42-45` keeps the mic open all the time. `main.swift:718-733` moves that always-open
  mic to whatever the Mac's default input becomes.
- **What goes wrong:** macOS can only use a Bluetooth headset's mic in its two-way call mode (HFP), and in that
  mode the headset's output also becomes low-quality, narrowband mono. Connecting AirPods usually makes them the
  default input. Voice follows, keeps the mic open, and the user's music and calls stay muffled for as long as
  Voice is running, not just while they talk. This is well-known macOS Bluetooth behaviour; I couldn't reproduce
  it here.
- **How to make it happen:** Leave the mic on "Same as the Mac", connect AirPods, and play music.
- **Suggested fix:** Don't keep a Bluetooth input open. Check the device's transport type
  (`kAudioDevicePropertyTransportType == kAudioDeviceTransportTypeBluetooth` / `BluetoothLE`) and open it only
  while the key is down, giving up the 0.6 s pre-roll on that device. Or prefer the built-in mic when the default
  input is Bluetooth, and say why in Settings.

### 5. Switching engines during a download can make dictations come back empty. **Fixed** (`cee4432`)

- **Where:** `Transcriber.swift:103-143` and `:241-251`. Only `prepareLive` (`:167-169`) checked `generation`.
  Audio is dropped at `Transcriber.swift:704-713`: Whisper, Fast and Instant sessions read `floatChannelData`
  only and silently drop anything else.
- **What goes wrong:** `prepare()` for an engine you have since left still sets the shared `format` and `state`
  when it finishes. Pick Whisper (a 626 MB download), then switch to Mac built-in before it finishes. The Mac
  engine becomes ready, then Whisper's load ends and sets the format to 16 kHz float and the state to ready under
  the Mac engine. The reverse order can leave the Mac engine's format under Whisper. *Unconfirmed:* whether that
  format is Int16 on macOS 26. If it is, the whole recording is dropped: the recorder delivers Int16 buffers,
  Whisper's `push` ignores them, and the result is "Didn't catch that".
- **Fix:** Every preparation path checks that it is still the current one before it sets the format, the state or
  the download progress.

### 6. Dictation goes into password fields and is saved in plain text. **Not fixed.** Likely

- **Where:** `FocusGate.swift:224` and `:243-250` judge by role only. A password field's role is `AXTextField`
  with subrole `AXSecureTextField`, and the subrole is checked nowhere. `main.swift:1661-1666` then records the
  text in `history.jsonl`, `lastSaid` and the word suggestions.
- **What goes wrong:** A dictation spoken while the cursor is in a password field is typed into it and kept in
  the history in plain text, readable by the user's account. It is also offered by Paste last and shown in the
  History window. *Unconfirmed:* whether macOS secure input lets the talk key's events reach Voice while a
  password field has focus. If it doesn't, the dictation never starts there.
- **Suggested fix:** Read `kAXSubroleAttribute`. For `AXSecureTextField`, either refuse ("Voice doesn't type into
  password fields") or type the text but never record it in history, stats text, suggestions or `lastSaid`.

### 7. A frozen app can freeze Voice for seconds at a time. **Not fixed.** Likely

- **Where:** Every Accessibility call runs on the main thread with the default timeout. Nothing calls
  `AXUIElementSetMessagingTimeout`. For example, `begin()` at `main.swift:749-753` calls `Insert.focus()`,
  `focusedElement()`, `boxWindow`, and `boxPrint`, which walks up to 40 parents (`:1317-1327`). `HUD.captureScreen`
  then asks for the focused window too (`HUD.swift:38-52`).
- **What goes wrong:** When the app in front is beachballing, each AX call waits up to the system's messaging
  timeout. Apple doesn't document the default; it is commonly reported as about 6 s. Pressing the talk key there
  stalls Voice's main thread, so the bar, the key-release handling and the shortcuts all wait. Releases are
  recovered later by the 0.2 s hardware check, but the dictation can start and end seconds late.
- **How to make it happen:** Focus a text box in an app that is hung (stop it with `kill -STOP <pid>` after
  focusing its box) and hold the talk key.
- **Suggested fix:** Call `AXUIElementSetMessagingTimeout(AXUIElementCreateSystemWide(), 0.5)` once at launch,
  and the same on each `AXUIElementCreateApplication` element, which the system-wide setting doesn't cover.

### 8. ⌃⌥S (swap a marked word) stops working after the first dictation. **Fixed** (`50cab47`)

- **Where:** `main.swift:890` registers Escape with `Shortcut(id: 3, ...)` at every press. `main.swift:1850`
  registers ⌃⌥S with `Shortcut(id: 3, ...)`. `Shortcut.swift:18` keeps one action per id, and `deinit` never
  removes it.
- **What goes wrong:** The first dictation replaces id 3's action with `discard()`. From then on, ⌃⌥S calls
  `discard()`, which with no dictation running does nothing. Turning the setting off and on again restores ⌃⌥S,
  but only until the next dictation.
- **How to make it happen:** With Whisper, turn on "Point out words to check", dictate until a word is marked,
  then press ⌃⌥S.
- **Fix:** The ids now come from a `ShortcutID` enum, so the compiler rejects a duplicate. Escape is id 4.

### 9. Changing the mic in Settings during a hands-free dictation cuts that dictation's audio. **Not fixed**

- **Where:** `main.swift:1995` calls `warmMic()` on any mic change. `Recorder.start()` calls `stopEngine()`, which
  sets `live = nil`.
- **What goes wrong:** The rest of the running dictation is never recorded, and nothing says so.
- **How to make it happen:** Tap twice to go hands-free, open Settings and pick another mic, keep talking, then
  tap to stop. Only the words before the switch come out.
- **Suggested fix:** If `session != nil || writing > 0`, save the choice and restart the mic when the dictation
  ends, as `remicIfDefaultMoved` already does for the default input.

### 10. "Record a test" during a hands-free dictation took that dictation's audio. **Fixed** (`2b2a725`)

- **Where:** `main.swift:1910-1931`. `Recorder.begin()` replaces the one audio callback, and `end()` later calls
  `recorder.end()`, which cut the test recording off.
- **Fix:** A test recording now waits until no dictation is recording or being written.

### 11. Sleep and wake are not handled. **Not fixed.** Unconfirmed

- **Where:** The only wake observer in the app is the Stats window's (`StatsWindow.swift:48`). The warm
  `AVCaptureSession`, the CGEvent tap and the HUD screen choice get no sleep or wake handling.
- **What may go wrong:** If capture doesn't resume after a long sleep, or the audio device is re-created on
  wake, presses after wake record nothing until the mic is restarted. The fix for #3 catches the case where the
  device posts a disconnect; it can't catch a capture session that silently stops delivering. A hands-free
  dictation across a lid close keeps going after wake. That's harmless, but the first word after wake may be
  missing.
- **Suggested fix:** On `NSWorkspace.didWakeNotification`, if no dictation is running, call
  `recorder.stopEngine(); warmMic()`. More robust: record when the last buffer arrived and restart the mic at the
  next press if none has arrived for several seconds.

### 12. Hands-free has no time limit. **Not fixed**

- **Where:** Nothing ends a hands-free dictation except a tap, Escape or quitting. Each pass of the stream loop
  copies the whole recording (`Transcriber.swift:486`, and the draft loop at `:451`), because holding `samples`
  while `push` appends forces a full copy.
- **What goes wrong:** If you forget hands-free is on, Voice keeps recording the room. Memory grows by about
  230 MB an hour of audio, plus 5 to 7 full copies a second of everything recorded so far (several GB/s of copying
  after an hour). Escape is taken from every app for the whole time (`main.swift:890`). The words, including
  other people's, are typed live into the box (Whisper) and kept in history.
- **Suggested fix:** Stop after a long stretch of silence (for example 60 s) or a hard cap (for example 15 min),
  with a warning in the bar first. Keep `samples` in chunks, or copy only the audio after `cut`, so each pass does
  a fixed amount of work.

### 13. A chosen mic that comes back is never used again. **Not fixed**

- **Where:** `Recorder.swift:74-75` (a missing chosen mic silently falls back to the default) and `main.swift:728`
  (`remicIfDefaultMoved` returns early unless "Same as the Mac" is chosen).
- **What goes wrong:** If you chose a USB mic and it was unplugged at launch (or reconnected after #3's fix fell
  back to the default), Voice stays on the built-in mic after you plug it back in. The menu shows the fallback's
  name, but Settings still shows your chosen mic as selected.
- **Suggested fix:** Listen for `kAudioHardwarePropertyDevices` changes. When the chosen UID reappears and no
  dictation is running, restart the mic on it.

### 14. On a second display, the bar could be placed off screen or on the wrong screen. **Partly fixed** (`8176e79`)

- **Where:** `HUD.swift:29` and `:57` keep the `NSScreen` chosen at key-down. `:273-279` places every later
  message with it.
- **What went wrong:** Messages can come minutes later ("Saved for X…" waits up to 10 minutes). After undocking,
  the stale `NSScreen` could put the bar off screen where nobody sees it. **Fixed:** the display is looked up again
  by its number, with the pointer's screen as the fallback.
- **Still open:** Every later message goes to the display of the *last dictation*, even a ⌃⌥V "Pasted" pressed on
  another display an hour later. Clear `dictationScreen` once a dictation's own messages are done.

### 15. Typing split emoji and accented letters. **Fixed** (`d3da182`)

- **Where:** `Insert.swift:470` and `:490-492` cut `text.utf16` every 20 units.
- **What went wrong:** An emoji (two UTF-16 units) or a letter with a combining accent that straddled unit 20 was
  posted as two halves, which apps show as a broken character (often `�`). It shows up on longer dictations
  that contain emoji or decomposed accents, for example from the names list.
- **Fix:** `TypingChunks.split` cuts only between whole characters.

### 16. A second copy did a full startup before quitting. **Fixed** (`0a50fc7`)

- **Where:** `main.swift:526-554` ran before the lock check at `:557`.
- **What went wrong:** A copy opened by hand while one is running (or racing the watchdog's reopen) added a second
  menu-bar icon, started the key watchers and the CGEvent tap, tried to register the shortcuts, started loading
  the speech engine and, without Accessibility, showed the first-run window, then exited a moment later.

### 17. Log lines could interleave or be lost. **Fixed** (`e219704`)

- **Where:** `Log.swift:353-363`. Lines come from the main thread, the mic queue (`Recorder.swift:104`), the key
  listener's thread, CoreAudio tap queues and engine tasks.
- **What went wrong:** The counter, size check, delete-and-recreate and writes were unsynchronized, so lines could
  interleave, and a line could be lost when the log was recreated. **Fix:** a lock, and one date formatter
  instead of one per line.

### 18. Quitting can drop words. **Not fixed.** By design, but worth a look

- `main.swift:650-653`: quitting while a dictation is being written, but no key is held, quits at once and drops
  those words. Hands-free stops become writing within a second, so this is easy to hit.
- `main.swift:1675`: if two dictations are being written, the first to finish allows the quit, and the second
  one's words are lost.
- **Suggested fix:** Return `.terminateLater` while `writing > 0` too, and reply only when `writing` reaches 0.
  The new deadline (#1) keeps this from hanging.

### 19. When Paste last can't confirm, the user's clipboard is gone. **Not fixed.** Documented

- **Where:** `PasteAttempt.swift:395-400`. On failure the loan keeps the dictation on the clipboard, and the saved
  snapshot is dropped.
- The README does say the words stay on the clipboard for ⌘V. But whatever the user had copied before is lost
  for good, with no way back.
- **Suggested fix:** Keep the snapshot until the next change to the clipboard, and add a "Restore clipboard"
  action, or restore it automatically after about 30 s if the clipboard is still Voice's.

### 20. Legitimate text in parentheses or brackets is deleted. **Not fixed.** Unconfirmed how often

- **Where:** `Silence.swift:353` removes any `(…)`, `[…]` or `*…*` of up to 40 characters, wherever it appears,
  with any engine output.
- **What goes wrong:** "Meet at 3 (the usual room)" comes out as "Meet at 3". Whisper does write spoken asides in
  parentheses sometimes.
- **Suggested fix:** Remove a bracketed span only when it is the whole output, or when it matches known sound
  labels such as `[Music]`, `(applause)` or `*laughs*`.

### 21. Unsynchronized shared state. **Not fixed.** Unconfirmed impact

- `Recorder.level` is read on the mic queue (`Recorder.swift:105`) and set on main (`:126`, `:133`) with no lock.
- `Session.onPiece`, `onDraft` and `onCheck` are set on main (`Transcriber.swift:809`, `:833`) and read in
  detached tasks (`:459`, `:498`, `:524`) with no lock.
- `testFrames` is changed on the mic queue (`main.swift:1921`) and read on main (`:1936`).
- Closure-typed properties that are read and written at the same time are undefined behaviour in Swift and can
  crash. I'd expect it rarely, at the moment a dictation ends.
- **Suggested fix:** Guard each one with the lock that is already beside it, as `onPartial` already does
  (`Transcriber.swift:588-591`).

### 22. `Chunker.quietLevel([])` crashed. **Fixed** (`c451e1e`), latent

- **Where:** `Chunker.swift:330-334` read `sorted[count - 1]` with no check.
- Today's callers always hold at least one 30 ms frame, so I found no path that reaches it. But `hasSpeech` and
  `quietLevel` are public, and a shorter slice would crash in the middle of a dictation. It now returns the floor.

### 23. Draft-mode key matching assumes nanosecond event timestamps. **Unconfirmed**

- **Where:** `DraftInputMonitor.swift:271` divides `CGEvent.timestamp` by 1e9 and compares the result with
  `NSEvent.timestamp` and system uptime.
- Some reports say `CGEventTimestamp` is in Mach time units on Apple silicon, not nanoseconds. If that's true, no
  talk-key down would ever match within 25 ms, and draft mode would stop at the first stop tap. The Oct 30 notes
  describe matches within 0.1 ms, which suggests the units are fine on that Mac.
- **Suggested fix:** Log both clocks once at launch, or convert with `mach_timebase_info` explicitly.

### 24. Small leaks and doubled work

- **Transcribe a file leaves a temporary file behind** when the transcription fails: the temp `.m4a` is removed
  only on success (`main.swift:1881`).
- **Whisper can be loaded twice. Unconfirmed:** Settings' "Download Whisper" (`SettingsWindow.swift:83-98`) and
  `prepare()` can both pass `guard whisper == nil` in `fetchWhisper` (`Transcriber.swift:266`) and both load
  WhisperKit. That holds about 1.2 GB of memory briefly, and the last one to finish wins.

## Speed

- **The history is reread too often.** `menuState()` rereads and parses up to 2,000 JSON lines of history on
  every `refreshMenu()` (`main.swift:1771`). That happens after every dictation, every engine state change and
  every percent of a model download. Settings rereads the whole history file on every redraw for its count
  (`SettingsWindow.swift:110-112`). Keeping the last entry and the count in memory would avoid both.
- **Long hands-free dictations copy everything recorded, several times a second** (#12). The end-of-dictation
  checks also scan the whole recording on the main thread: `endedQuiet` (`Transcriber.swift:533`) and
  `talk.add(s.recorded, …)` (`main.swift:1657`).
- **FixWatch reads the whole text box every second** for two minutes after each dictation, on the main thread
  (`FixWatch.swift:146-157`). In a long document that is a large Accessibility copy every second. Reading only
  the range around the dictation (`kAXStringForRangeParameterizedAttribute`) would be much cheaper.
- **The first-run and Settings mic pickers enumerate CoreAudio devices on every redraw** (`FirstRun.swift:260`,
  `SettingsWindow.swift:388-389`). The first-run window redraws whenever the mic level changes, which happens for
  every audio buffer.
- **The 0.25 s media check runs on every press** where any app holds audio output, before the pause decision.
  That is by design, but each check creates and destroys a CoreAudio process tap and aggregate device. It's
  cheap, but it shows up in Audio MIDI Setup and other audio tools as a device flickering in and out.
- **Accessibility calls with no timeout** (#7) are the most likely cause of "Voice froze for a few seconds".

## Privacy

- **Password fields** (#6). This is the one I'd fix first. A dictated password would sit in `history.jsonl` in
  plain text.
- **The mic is always open**, with the orange dot lit. This is disclosed in the README and Settings. With
  Bluetooth headsets it also degrades their audio (#4), which is not disclosed.
- **A forgotten hands-free dictation records the room indefinitely** and types what it hears (#12).
- **`word-suggestions.json` stores candidate names in plain text** (up to 256). It is cleared when history is
  "Nothing", but kept indefinitely when history is "The last week". The README describes the file accurately.
  Consider tying it to the week setting too.
- **The Settings footer always says the text of dictations is kept "(the last 2,000)"**, even when History keeps
  a week or nothing (`SettingsWindow.swift:459`). It should follow the chosen setting.
- **The log is clean.** It records app names, focus roles, timings and counts, with no dictated text. It is mode
  0600. The raw talk-key lines (`HoldKey.swift:131-141`) turn themselves off on 2026-11-05.
- **Network use matches the README:** Hugging Face for the models, Apple for its speech files, and a daily
  GitHub check by Sparkle.
- **When Paste last can't confirm, the user's previous clipboard is gone for good** (#19).

## What a first-time user would trip on

1. **Up to four permission prompts, one of them mid-dictation.** The first window covers Microphone and
   Accessibility. Speech Recognition is requested at every launch (`main.swift:532`), even for Whisper or Instant
   users, who may not need it (*Unconfirmed*). The system-audio recording prompt appears the first time something
   is playing when the talk key goes down (`SoundTap.swift:69`). That's a surprising moment for a system dialog,
   and the first window never mentions it, although `SystemSettingsLink.systemAudio` exists.
2. **Right Option is a default talk key, which clashes with non-US keyboards.** Polish, German, French and other
   layouts type characters with Option held (`HoldKey.swift:15`, default `fnOrOption`). Each such character
   starts and cancels a dictation, with a click each time if "Click at start and stop" is on.
3. **Escape is taken from every app while a dictation runs** (`main.swift:890`). In a long hands-free dictation,
   Escape in another app (closing a dialog, leaving full screen) throws the dictation away instead.
4. **Bluetooth headsets sound worse as soon as Voice is running** (#4), and it isn't obvious why.
5. **A new press is refused while the last dictation is still being written** (`canBegin`, `main.swift:537-540`).
   For about 0.5 s plus Whisper's ending time after you let go, holding the key again does nothing, with no
   message. A short "Still writing…" flash would explain it.
6. **The default engine is Mac built-in**, which the app's own numbers say is the least accurate (12.0% of words
   wrong). Done can't be clicked until it is ready, which may mean waiting for Apple's speech files to download.
7. **Secure keyboard entry** (Terminal's setting, some password managers) may stop the talk key from reaching
   Voice while it is on. *Unconfirmed*, but if so, nothing tells the user why.
